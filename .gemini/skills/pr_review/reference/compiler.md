# Compiler & Compiler-CLI PR Review Guidelines

When reviewing pull requests that modify the Angular Compiler (`packages/compiler`) or Compiler-CLI (`packages/compiler-cli`), pay special attention to the following areas:

- **Template Pipeline Architecture**: Keep the `ingest` phase as clean and faithful to the source HTML/AST as possible. Avoid special casing or context building during ingestion. Instead, generate standard operations (like `ir.BindingOp`) and rely on dedicated downstream phases to convert them into specialized operations.
- **AST and Parsing**: Do not make assumptions about expression types (e.g., assuming an expression is always a `PropertyRead`). Always use the binding parser to properly parse text into an AST structure. Maintain accurate `ParseSourceSpan`s to ensure high-quality error reporting and diagnostics.
- **Code Generation APIs (Instructions)**: Ensure all runtime instructions generated by the compiler have proper JSDoc comments and are annotated with `@codeGenApi`. Pay close attention to instruction chaining compatibility (e.g., `CHAIN_COMPATIBILITY`) and the correct `TView`/`LView` context (differentiating between host and embedded views).
- **Performance & Tree-Shaking**: Group conditionally enabled code (such as hydration logic or specific control flows) together to make code switches evident and ensure efficient tree-shaking. Place related initialization or cleanup paths into unified functions to avoid scattering logic.
- **Code Style**:
  - Prefer explicit equality checks (e.g. `x === null` or `x !== undefined`) rather than relying on truthiness (`!x`).
  - Prefer early returns over deeply nested branches to keep the main logic at the highest level of indentation.
  - Avoid unnecessary allocations (e.g., combine bitwise flags directly rather than putting them in arrays first).
- **Testing**: Rely heavily on `compliance` tests (`packages/compiler-cli/test/compliance/`) for verifying generated code and TCB outputs. Avoid duplicating these tests with other parallel flavors. Ensure new diagnostics include tests covering both the error and successful states, especially for edge cases like global event targets (`window:`, `document:`).
