# Coding Guidelines & Best Practices

When working on this codebase, adhere to the following rules:

1. **Production Quality Code**: Ensure all code uses production-grade methods (e.g., no magic string regexes, lookups, etc. Use `oxc` AST interfaces correctly).
2. **Semantic Symbol & Scope Resolution (`oxc_semantic`)**: Always resolve identifiers, types, imports, and scope bindings through `oxc_semantic` (`Semantic`, `Scoping`, `SymbolFlags`). Look up the `reference_id` on AST nodes (`ident.reference_id.get()`), query `scoping.get_reference(ref_id).symbol_id()`, inspect flags with `scoping.symbol_flags(symbol_id)`, and navigate to declarations with `semantic.symbol_declaration(symbol_id)`. This guarantees proper lexical scoping and handles shadowed symbols correctly.
3. **AST-Driven Code Transformations**: Perform all code rewrites, qualification, and emission using AST transformations or exact AST source spans (`oxc_span::Span`) with range-based splicing (e.g., `MagicString`). Avoid regex replacements on code strings to prevent corrupting string literals, property keys, or colliding identifiers.
4. **TypeScript Accuracy**: Keep TypeScript types strict and accurate. Ensure all TS code passes `noEmit` type-checking.
5. **Feature Parity**: Always verify your changes against the `@angular/compiler-cli` and `@angular/compiler` reference code. We are rewriting components and looking for feature parity. Add explicit `TODO` comments where reaching parity is not currently possible.
6. **Shared Utilities**: Check for and utilize shared helper functions (e.g., in `ng-analyze/src/analyzer/utils.rs`). When extracting properties from AST, always use helpers like `extract_property_key` or `extract_string` to correctly handle AST variants (like `StringLiteral`, `TemplateLiteral`, or `NumericLiteral`), ensuring you don't miss data that the compiler-cli handles properly.
7. **Early Returns (`let...else` and `?`)**: In Rust and TypeScript, avoid deeply nested `if let` and conditional blocks. Prefer flattening the code structure using early returns. For matching `Option`/`Result` within functions returning those types, rely on the `?` operator for automatic early returns. When you cannot use `?` (e.g., returning specific fallback values or needing to `continue` in a loop), use `let ... else` blocks (e.g., `let Some(x) = y else { return false; }`). This mimics the flat structure and early-return style consistently used in `compiler-cli`.
   - **Nesting Alert**: It is very easy to accumulate nested `if let` or `if` blocks. Pay extra attention to these during reviews.
   - **Helper Functions**: If direct un-nesting via `let else { continue; }` is unsafe (e.g., it would skip other necessary processing in a loop), extract the nested block into a descriptive helper function to safely use early returns.
8. **Consolidate AST Analysis into Existing Visitors & Extractors**: The analyzer already performs extensive AST and file analysis across source files and definition files (`.d.ts`). Integrate new features, fixes, and metadata extraction directly into the existing, appropriate analysis passes (such as `visitor.rs`, `dts.rs`, or shared extractors in `analyzer/utils/mod.rs`). When an existing visitor or helper already visits a node or inspects its symbols (such as type parameter constraints, class members, or decorator metadata), extend that pass to collect the additional information in a single traversal.
9. **Single Source of Truth for Paths & Module Resolution (Rust Analyzer Only)**: All filesystem knowledge, module specifier resolution, path diffing/joining, and import emit strategies (`ReferenceEmitStrategy`, `ApfImportStrategy`, `PrefixImportStrategy`) belong strictly in the Rust `ng-analyze` layer. The TypeScript layer (`src/tcb.ts`, `src/processor.ts`, `src/tcb_adapter.ts`, etc.) is a pure downstream code generator that consumes pre-resolved metadata emitted by `ng-analyze`. The TypeScript layer MUST NOT perform manual path manipulation, `path.dirname`/`path.join` rebasing, module resolution, or ad-hoc path arithmetic on module specifiers. If a module specifier or import path is incorrect in emitted code, the resolution logic MUST be implemented in the analyzer's reference projection and import emit strategies in Rust, not in TypeScript glue code.
10. **Cross-File Reference Projection Across Frames**: Metadata extracted from AST during single-file analysis is evaluated in the frame of the declaring file (e.g. raw relative imports like `./models`). When that declaration is consumed by a different file, NgModule scope, or serialized into wire metadata, all module specifiers and references MUST be projected into the consumer's frame via the query engine's `ReferenceEmitStrategy` (e.g. in `contextualize_declaration` and `ClassData::to_wire`). Never leak raw declaring-file-relative specifiers into consumer metadata.
11. **Matching `ngtsc` Strictness & Diagnostics**: Match the exact behavior and strictness of `ngtsc`. We must not be more permissive than `ngtsc`. If `ngtsc` produces diagnostics or errors for a pattern or construct, this preprocessor should produce diagnostics as well rather than silently allowing or forgiving invalid code.
